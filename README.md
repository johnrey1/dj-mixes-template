# dj-mixes

A $0/month site for streaming DJ mixes to friends via a plain link — no accounts, no app installs.

- **Storage**: Cloudflare R2 (free egress, 10GB free tier)
- **Frontend**: static HTML/CSS/JS in [`site/`](site/), no framework, no build step
- **Hosting**: Cloudflare Pages, auto-deploys on every push to `main`
- **Manifest**: [`site/mixes.json`](site/mixes.json), fetched client-side, one entry per mix

## Repo layout

```
site/            deployed to Cloudflare Pages as-is (output dir = site/, no build command)
  index.html
  styles.css
  config.js      site branding + category labels — edit this to make it yours
  app.js
  mixes.json     manifest — regenerated by scripts/add_mix.py
scripts/
  add_mix.py             CLI: upload a mix to R2 + register it in mixes.json
  requirements.txt
  requirements-dev.txt   test deps (pytest) — layers on top of requirements.txt
  tests/                 pytest suite for add_mix.py's pure helpers
  r2_config.example.env
.github/workflows/ci.yml runs the pytest suite on push / PR
```

Run the tests with `pip install -r scripts/requirements-dev.txt && pytest scripts/tests`.

Only `site/config.js`, the `<title>` in `site/index.html`, and `site/mixes.json` are meant to differ from the template — everything else tracks it (see [Using this template](#using-this-template)).

## Using this template

Use this repo as a GitHub template (**Use this template → Create a new repository**), or:

```bash
gh repo create <your-repo> --public --template johnrey1/dj-mixes-template --clone
```

Then follow *Make it yours* below.

**Updating later.** `site/app.js`, `site/styles.css`, and `scripts/` are meant to stay identical to the template. To pull in fixes, download the template again (**Code → Download ZIP**), copy those paths over yours, then `git diff` and commit. Don't copy `site/config.js`, `site/mixes.json`, or `site/index.html` — those are yours.

## Make it yours

Before doing any Cloudflare setup, customize the branding:

1. Edit [`site/config.js`](site/config.js) — site name, tagline, and the three category labels (`recording`/`live`/`event`). The file has the exact fields; just replace the values.
2. Also update `<title>` in [`site/index.html`](site/index.html) to match your `siteName`. This is intentionally a separate, static edit (see the comment above it in the file) — link-preview scrapers (iMessage, Slack, Discord) typically read `<title>` without running JS, so it can't be config-driven the way the rest of the header is.
3. Confirm `site/mixes.json` is `[]` — an empty array, ready for your own mixes.
4. Colors and fonts are CSS custom properties at the top of [`site/styles.css`](site/styles.css) if you want to reskin beyond the defaults.
5. Exactly three fixed categories are supported (`recording`/`live`/`event`) — renaming their labels is just a `config.js` edit, but adding a fourth category needs code changes (`FILTERS`/`TYPE_LABELS` derivation in `app.js`, and the `--type` choices in `add_mix.py`). If you don't use the `event` category at all, that's fine — its filter pill just never has anything in it. Note also: if you ever remove a category from `config.js` after already uploading mixes tagged with it, those mixes don't disappear or error, they just silently relabel as `recording` — a config.js edit doesn't touch already-uploaded mix data.

## One-time Cloudflare setup

### R2 bucket + API token

1. Create a free Cloudflare account.
2. Dashboard → R2 → Create bucket → give it any name you like (it's just an internal reference, not shown to visitors).
3. Enable public access (Settings → Public Access → the built-in `r2.dev` subdomain, or a custom domain later).
4. **Set a CORS policy on the bucket** (Settings → CORS Policy → Add) — without this, the waveform player breaks silently, because it fetches audio via `fetch()` (not a plain `<audio>` tag) to draw the waveform, and R2 buckets have no CORS policy by default:
   ```json
   [
     {
       "AllowedOrigins": ["*"],
       "AllowedMethods": ["GET", "HEAD"],
       "AllowedHeaders": ["*"],
       "ExposeHeaders": ["ETag", "Content-Length", "Content-Range", "Accept-Ranges"],
       "MaxAgeSeconds": 3600
     }
   ]
   ```
   Do this in the **Cloudflare dashboard**, not via a script using the API token from the next step — that token is scoped to object read/write only and will get `AccessDenied` on bucket-level settings like CORS.
5. Create an R2 API token (Manage R2 API Tokens) scoped to just this bucket, with read + write permission.
6. Copy `scripts/r2_config.example.env` to `.env` in the repo root and fill in:
   `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` (the name you picked in step 2), `R2_PUBLIC_URL`.
   `.env` is gitignored — never commit it.

### Deploy to Cloudflare Pages

Cloudflare's dashboard has moved Pages behind a Workers-first flow — it's easy to miss:

1. Push your repo to GitHub (your copy from [Using this template](#using-this-template)).
2. Cloudflare dashboard → **Workers & Pages** in the sidebar → **Create application**. This opens a "Create a Worker" flow by default — scroll to the bottom and click **"Looking to deploy Pages? Get started"** to reach the actual Pages flow.
3. **Import an existing Git repository** → connect your GitHub account → select this repo.
4. Build settings:
   - Framework preset: **None**
   - Build command: **`exit 0`** (a static site with no build step still needs *something* here — this is Cloudflare's documented no-op; leaving it empty won't save)
   - Build output directory: **`site`**
5. Save and Deploy. First build can take a couple of minutes on a fresh account; later ones are usually under a minute.
6. You'll get a `*.pages.dev` URL — that's the link to share with friends. A custom domain can be added later (Custom Domains tab) if you want.

## Adding a mix

One-time setup:

```bash
pip install -r scripts/requirements.txt
mkdir -p local_mixes   # gitignored — drop your exported mp3 masters here, they never get committed
```

Runbook, each time you have a new mix ready:

1. Export/render the finished mix as an **mp3** and drop it in `local_mixes/` (e.g. `local_mixes/2026-07-29-progressive-trance-vol-12.mp3`). Non-mp3 files are rejected — convert first if needed.
2. Run the CLI against it:
   ```bash
   python scripts/add_mix.py local_mixes/2026-07-29-progressive-trance-vol-12.mp3 \
     --title "Progressive Trance Vol. 12" --bpm "132-136" --notes "Solarstone-leaning set"
   ```
3. It uploads to R2 under `mixes/<id>.mp3`, prepends an entry to `site/mixes.json`, and prints the `git add/commit/push` command to run next.
4. Run that command. Pushing triggers a Cloudflare Pages redeploy in ~30-60s.
5. Check the live site to confirm the new mix appears and plays.

Mixes fall into three categories via `--type` (defaults to `recording`):

- `recording` — a mix you recorded at home (default)
- `live` — a live set you played
- `event` — a set from a recurring event of yours, played by someone else; requires `--artist "DJ Name"` and accepts `--event-name "Your Event Name 2026"`

```bash
python scripts/add_mix.py local_mixes/2026-05-01-closing-set.mp3 --title "Closing Set" --type event --artist "DJ Someone" --event-name "Your Event Name 2026"
```

The site shows filter pills for whatever category labels you set in `config.js`, so friends can browse by category.

Other flags:
- `--date YYYY-MM-DD` — defaults to today if omitted.
- `--force` — re-running with the same title + date normally aborts (won't silently overwrite an existing mix in R2 or the manifest); pass `--force` if you actually mean to replace it.
- `--suggest-timestamps` — propose a **rough** start time for every tracklist entry that has no explicit timestamp (see below) and write the result into the manifest. It reads a timbre/harmony novelty curve (MFCC + chroma self-similarity, à la music structure segmentation — not loudness) off the audio, moves each even-split guess to the nearest transition, and snaps it to the nearest detected beat. Treat the result as a draft to hand-correct in `git diff`, never ground truth: long seamless blends are engineered to have no single transition point and can be off by 10–30 s. **If you played or recorded the set in Rekordbox / Serato / Traktor, use its History export instead** — it already logged every track load with a timestamp; just prefix the tracklist lines with `[mm:ss]` from that. Entries you timestamp by hand are kept as-is and used as anchors. Needs a tracklist in the `USLT` tag and `ffmpeg` on `PATH`; without `ffmpeg` (or without `librosa`, an install dependency) it falls back to a plain even split. See [`docs/timestamp-detection.md`](docs/timestamp-detection.md) for the signal-choice rationale.
- `--suggest-only` — print the suggested tracklist and exit. No R2 upload, no manifest write, no credentials needed — use it to preview before committing to `--suggest-timestamps`.

Two things happen automatically from the mp3 itself, no flags needed:
- **Tracklist**: if the file has a `USLT` (lyrics) tag with one track per line, it's pulled in and shown as an expandable "tracklist" disclosure on the site. A line may start with a timestamp so listeners can jump straight to that track and copy a link to that exact point (`?mix=<id>&t=<seconds>`). Accepted forms — `[12:34] Artist – Title`, `(12:34) Title`, `12:34 - Title`, or `12:34` followed by two-plus spaces then the title. A bare `12:34 Title` with a single space is treated as plain text (so a title like `2:54 AM - Someone` survives). Lines with no timestamp still work exactly as before.
- **Waveform peaks**: if [`ffmpeg`](https://ffmpeg.org) is installed locally, the script pre-computes waveform peak data and stores it in the manifest, so the site renders the waveform instantly instead of downloading and decoding the whole file in-browser (matters most for hour-long live sets). Without `ffmpeg`, mixes still work fine — the site just falls back to decoding the file client-side, which is slower to render for long mixes.

## Custom domain (optional)

Not required — the free `*.pages.dev` URL works fine for sharing with friends. If you want a custom domain later: Cloudflare Pages → your project → Custom Domains → Add. For a subdomain (e.g. `mixes.yourdomain.com`), you don't need to move your domain's DNS to Cloudflare — add the custom domain in the Pages dashboard first (it'll show you a CNAME target), then add that CNAME record wherever your domain's DNS already lives.
